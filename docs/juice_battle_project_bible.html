The Five Concepts — Complete Reference

Everything in the firmware is an application of exactly one of these five concepts. Understand the concept before touching the code.

Concept 1 — σ and the Noise Floor

σ (standard deviation) is the noise floor expressed in grams. It is the single number that sets every threshold in the entire system. Without measuring it in the real environment first, every threshold is a guess.
  • One ADC sample has uncertainty ±σ. Averaging N samples gives ±σ/√N.
  • ADS1232 theoretical floor: 17nV ÷ (2mV/V × 5V ÷ 5000g) ≈ 0.085g per sample. Real-world σ_live in a noisy stall: 10–30g.
  • σ_quiet = measured at rest in lab conditions. σ_live = measured WITH motor, music, crowd. Use σ_live for all thresholds.
  • Every weight reading in the result struct includes sigma_g alongside value_g.
  • 68% of readings fall within ±1σ. 95% within ±2σ. 99.7% within ±3σ.
// Noise floor measurement (node.ino → noise.cpp)
sigma_g = measure_sigma(n_samples=100, adc_driver)
// Returns result struct: {sigma_raw, sigma_g, quality, diagnosis}

Concept 2 — Stability Detection

The state machine IS stability detection. Slope + persistence detects pour start. Spread confirms settlement. These are the two instruments: one for change, one for quiet.
  • Slope estimate: (EMA[i] − EMA[i−M]) / M × SPS in g/s. Stable=≈0, Pouring=−40g/s.
  • Persistence: require K consecutive samples below slope threshold before firing POURING. Rejects bumps (short transients). K=3–5 at 10 SPS.
  • Spread check: rolling std dev of last N samples. Used in SETTLING state to confirm quiet before reading new baseline.
  • Slope threshold derived from σ_live: threshold = 2.5 × σ_live × √2 × SPS / M. If SNR < 1.5×, increase N before proceeding.

Concept 3 — Averaging and What It Cannot Fix

Averaging kills exactly one class of error: zero-mean random noise. It has zero power against bias, gain error, nonlinearity, drift, or creep. Match the tool to the error type.
Error classAveraging fixes?What actually fixes it
Random noise✓ Yes — σ/√NAveraging (EMA for runtime, block avg for cal)
Systematic offset (bias)✗ NoTare / zero calibration
Gain error✗ NoSingle-point calibration (minimum)
Nonlinearity✗ NoMulti-point calibration (3-point piecewise)
Thermal drift✗ NoRe-tare at each game reset. Temperature compensation if needed.
Creep✗ NoMechanical design + wait time after loading
  • EMA for runtime: ema = α × new_sample + (1−α) × ema. α = 2/(N+1). One variable stored. Lower lag than MA for same noise reduction.
  • Block average for calibration: 50 independent samples → true √N applies. Use this only during confirmed STABLE state.
  • Never stack filters blindly. Each filter adds lag, phase shift, distortion. Add one only when you can name the specific error class it addresses.

Concept 4 — Nonlinearity and Multi-Point Calibration

Single-point calibration fits a straight line to a curved reality. The error is parabolic — zero at the calibration point, growing toward the extremes. Three points detect AND correct this. The residual spread between the three cal_factors IS the nonlinearity expressed as a number.
// Piecewise linear conversion — cal.cpp
float u = raw - raw_zero;
if      (u <= u1) weight_g = (u / u1) * 100.0f;
else if (u <= u2) weight_g = 100.0f + (u-u1)/(u2-u1) * 150.0f;
else              weight_g = 250.0f + (u-u2)/(u3-u2) * 250.0f;
// u1=raw_100-raw_zero, u2=raw_250-raw_zero, u3=raw_500-raw_zero
  • Max error: single-point ≈ ±3g across 0–500g range. Three-point piecewise ≈ ±0.25g.
  • Confidence score: spread = max(cf1,cf2,cf3) − min(cf1,cf2,cf3). confidence = 1 − spread/nominal/MAX_ACCEPTABLE. If confidence < 0.85 → DEGRADED, refuse game start.
  • For Juice Battle (0–500g on 40kg cell): nonlinearity is likely <0.5g — small but worth verifying. The confidence score gives this verification automatically.

Concept 5 — The Mode-Aware Pipeline

The pipeline has two fundamentally different operating modes. A single static filter cannot be optimal for both. The state machine switches between them. This is not adaptive filtering — it is a deliberate mode switch driven by physical reality.
ModeStateFilter strategyWhy
Baseline trackingWAITING_FOR_POUREMA with slow α (large N equivalent). Block avg for cal samples.Jar sitting still. Maximise accuracy. Lag is acceptable.
Pour detectionPOUR_IN_PROGRESSEMA-based slope. Small M. Persistence counter.Weight actively falling. Need fast response. Accept higher noise.
Settling guardSETTLINGSpread monitor. Fixed N-sample wait.Filter hasn't caught up yet. Premature baseline read = wrong delta.

Complete Calibration Sequence

1. TARE PHASE
   - Guard: if weight > TARE_MAX_GRAMS → FAILED (something on platform)
   - Capture 50 block-averaged samples → raw_zero
   - Compute σ_tare from the 50-sample window
   - Report: {raw_zero, sigma_tare_g, quality, diagnosis}

2. NOISE CHARACTERISATION (σ_live)
   - Sample 100 reads at rest WITH environment running (motor, music)
   - Compute σ_live in grams
   - Derive slope_threshold and persistence K from σ_live
   - Report: {sigma_quiet_g, sigma_live_g, snr_estimate, quality}

3. THREE-POINT CALIBRATION
   - For each weight in [100g, 250g, 500g]:
     a. Wait for STABLE (spread < σ_threshold)
     b. Capture 50 block-averaged samples
     c. Compute cal_factor_N = weight_g / (raw_avg - raw_zero)
   - Compute residuals, confidence score
   - Store raw_100, raw_250, raw_500 in NVS
   - Report: {cf[3], confidence, residual_max_g, quality}

4. POUR VALIDATION GATE (new — did not exist in previous projects)
   - Operator pours exactly 200ml of water
   - Node detects pour, measures delta_g
   - Hub checks: |measured - 200| / 200 < ERROR_PCT_THRESHOLD (e.g. 5%)
   - Pass → calibration locked. Fail → FAILED, reason reported, recalibrate.

5. GAME_READY
   - Both nodes must pass all 4 phases
   - Hub compares cal_factors between Node A and Node B
   - Large divergence → flag wiring or load cell problem
   - Issue start_game(glass_volume_g) only after both nodes pass

Node State Machine — Complete Reference

One node. One jar. Ten states. This is the complete firmware state machine for an ESP32-C3 node.

⏸ IDLE
Boot state. EMA init. BLE advertising. Waiting for hub command. No cal data loaded. Exits: hub sends calibrate.
🔧 CALIBRATING
Runs 4-phase calibration sequence. Emits CAL_COMPLETE {confidence, sigma_g, residual_max_g, cal_pts}. Exits to GAME_READY on pass, IDLE on fail.
✓ GAME_READY
Cal confirmed. Captures fresh baseline. Measures σ_live. Derives thresholds. Emits READY {baseline_g, sigma_live_g, snr_ratio, threshold_g_per_s}. Exits: hub sends start_game(glass_volume_g).
👁 WAITING_FOR_POUR ← HOME STATE
EMA running. Slope computed. Persistence counter active. Heartbeat every 2s: {weight_g, sigma_g, state, glass_count}. Watches positive delta (weight added = cheat). Exits: K consecutive samples below slope threshold.
🍹 POUR_IN_PROGRESS
Pour confirmed. Duration tracked. Emits POUR_START {baseline_g, timestamp_ms}. Mid-pour cheat watch: slope reversal → CHEAT_ALERT immediately. Does NOT update baseline. Exits: K consecutive samples above threshold.
⏳ SETTLING
Mandatory wait. N samples for EMA lag. Spread monitored — extends if spread > σ_threshold. Silent (no emits). Cannot be skipped. Exits: N elapsed AND spread < σ_threshold.
⚖ STABLE_SETTLED
delta_g = old_baseline − new_baseline (piecewise linear applied). Emits POUR_END {delta_g, new_baseline_g, duration_s}. Decision: δ≥glass→GLASS, 0<δ<glass→PARTIAL, δ≤0→CHEAT, δ<noise→ignore.
🥛 GLASS_COUNTED
δ + accumulated partial ≥ glass_volume_g. Emits GLASS_POURED {glass_num, delta_g, cumulative_g}. Accumulator reset. → WAITING_FOR_POUR. Hub: increment counter, run transparency check.
〜 PARTIAL_POUR
0 < δ < glass_volume_g. partial_accumulator += delta_g. Emits PARTIAL_POUR {delta_g, accumulated_g, remaining_to_glass_g}. → WAITING_FOR_POUR (accumulator preserved).
⚠ CHEAT_ALERT
Patterns: jar_lift (δ≈0 after pour), weight_added (δ<0), mid_reversal (slope positive during pour). old_baseline restored — cheat gains zero volume. Emits CHEAT_ALERT {pattern, delta_g, baseline_restored_g}. → WAITING_FOR_POUR.

BLE Payload Summary

HEARTBEAT:    {type, weight_g, sigma_g, state, glass_count}          // every 2s
POUR_START:   {type, baseline_g, timestamp_ms}                        // entering POUR_IN_PROGRESS
POUR_END:     {type, delta_g, new_baseline_g, duration_s, pour_num}  // entering STABLE_SETTLED
GLASS_POURED: {type, glass_num, delta_g, cumulative_g}               // GLASS_COUNTED
PARTIAL_POUR: {type, delta_g, accumulated_g, remaining_to_glass_g}   // PARTIAL_POUR
CHEAT_ALERT:  {type, pattern, delta_g, baseline_restored_g}          // CHEAT_ALERT
CAL_COMPLETE: {type, confidence, sigma_g, residual_max_g, cal_pts}   // end of CALIBRATING

Volume-Based Game Mechanics

Volume-based is superior to time-based for three reasons: (1) natural game mechanic — fill glasses not fill time, (2) fairness — slow careful pourers not penalised, (3) self-proving transparency — glass count and jar weight must mathematically agree.

Core mechanics

glass_volume_g  = set by operator before game (e.g. 200g ≈ 200ml for water/juice)
glass_count     = number of complete glasses poured from this jar
partial_accum   = grams carried forward from incomplete pours

// After each settled pour:
partial_accum += delta_g
if partial_accum >= glass_volume_g:
    glass_count += 1
    partial_accum -= glass_volume_g  // carry leftover forward

Transparency invariant (hub validates every heartbeat)

expected_weight = start_weight - (glass_count × glass_volume_g) - partial_accum
actual_weight   = current node weight_g
discrepancy     = |expected_weight - actual_weight|
if discrepancy > TOLERANCE_G:  # e.g. 10g
    flag: calibration_drift or anomaly detected

Cheat detection summary

Cheat attemptWhat the sensor seesDetection
Lift jar, put back (no pour)Weight drops, then returns to near original. delta ≈ 0.STABLE_SETTLED: delta < noise_floor after POUR event → jar_lift flag

Lift jar mid-pourSlope goes positive during POUR_IN_PROGRESS.Mid-pour slope reversal → CHEAT_ALERT immediately

Filter Philosophy

The single most important line from this entire design process:

"Good instrumentation is not about using many filters; it's about using the right filter for the error you're addressing."

Stacking Median → MA → EMA → Kalman → Butterworth → Savitzky-Golay produces a WORSE result, not a better one. Each filter adds delay, phase shift, distortion, and tuning complexity. Add a filter only when you can name the specific error class it targets.

Result Struct Contract

This contract is immutable. All C++ modules return this struct. Orchestrator (node.ino) acts only on quality, never on raw value.
// Every module returns this struct
struct WeightResult {
    float   value_g;        // calibrated weight in grams
    float   sigma_g;        // noise floor in grams (new — not in HX711 projects)
    Quality quality;        // GOOD / DEGRADED / FAILED
    char    diagnosis[64];  // human-readable reason if DEGRADED or FAILED
};

// Calibration result (extended)
struct CalResult {
    float   cal_pts[3];     // raw ADC at 100g, 250g, 500g
    float   confidence;     // 0.0–1.0 residual-based confidence
    float   residual_max_g; // max divergence between three cal_factors in grams
    float   sigma_g;        // noise floor at calibration time
    Quality quality;
    char    diagnosis[64];
};

What Not To Rebuild in Future Sessions

Do not re-discuss the calibration approach. Three-point piecewise linear is decided. No polynomial fitting. No Kalman for calibration. No single-point.
Do not stack filters without a named reason. The "should we use every filter?" question was answered: NO. Every filter addition must name the specific error class it targets.
Do not make the game time-based. Volume-based was chosen deliberately. The three reasons are documented in Game Mechanics section above.
Do not use the Kalman filter for pour detection. It was discussed and rejected. Kalman tuned for slow state changes (gas cylinder context) is wrong for a fast dynamic pour event. EMA + persistence is the correct tool here.
Do not attempt to build a "general-purpose precision weighing platform" with 10+ engines. That was the external AI's proposal. We are building a specific, purposeful system for Juice Battle. The 5 concepts are the complete design basis.
Do not skip noise.cpp. σ_live MUST be measured first in the real environment. If you write cal.cpp before noise.cpp, every threshold in the system is a guess.
